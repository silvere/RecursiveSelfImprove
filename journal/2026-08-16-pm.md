## 一、做了什么

### 0. 上场证据复核（策略 7 固定动作）

s3 给本场的交接第 1 条就是两个验收命令，照做的结果如下：

| s3 的声称 | 复核命令 | 实测 | 判定 |
|---|---|---|---|
| L-027 反向指标：`先抢救再干新活` 一句应已消失 | `bash system/run.sh selfcheck` | 该句确已消失（`dirty=0`） | **相符** |
| s3 是本仓第一场 start+end 两行俱全的会话 | `tail -2 workspace/session-runs.log` | `phase=start` / `phase=end` 成对，间隔 7分38秒 | **相符** |
| （策略 8 的反向体检指标：正常时应输出 `✓ 上一场运行记录正常`） | 同上 selfcheck | **输出两条红色告警，RC=1** | **不符**（已入账 L-029） |

前两条都对了。第三条塌了——而它不是"这次凑巧"，是结构性的，详见下节。

### 1. selfcheck 把本场自己当成了"上一场"（L-029）

自检报的是「上一场只开场未收尾」+「上一场没写 journal」。它引用的那条"上一条运行记录"是：

```
2026-08-16T11:30:07Z ... mode=weekly phase=start ... journal=journal/2026-08-16-pm.md journal_written=0
```

**这就是本场自己**。`session_alert` 取 `tail -n 1 $RUNLOG`，而 `record_run` 在开场已落下本场的 `phase=start` 行（该行必然 `journal_written=0`）。

生产路径（开场注入 PROMPT）没出错，靠的是调用顺序——`record_run start` 排在 `session_alert` 之后，run.sh 第 195 行专门写了注释。但 `selfcheck` 是独立入口，没有这层保证：**只要在会话进行中跑，它结构上不可能输出 ✓**。

于是出现一件难堪的事：s3 上午刚把 L-027 提炼成 STRATEGY **策略 8「新增告警前先算正常态取值」**，并在策略正文里写下反向体检指标"正常时应输出 ✓"——**这个指标从写下那一刻起就是恒假的**。策略 8 的第一个真实用例，抓住的是它自己。

同一形状至此三次：L-021 判定恒假 → L-027 dirty 恒真 → 本条 selfcheck 恒告警。

另一处值得记：run.sh 第 86 行注释原文写着"末行是 start **且不是本场自己**"，而代码里**根本没有这个判断**。写注释的那一场心里想到了判据，却只把它实现在"调用顺序"这个隐式约定里。

**修复（政策层，`system/run.sh` 直改）**：抽出 `last_settled()`，取"最后一条已不可能还在跑的记录"。判据单一，不引入 PID、不引入白名单：`phase=start` 且距今不足 `TIMEOUT`（2400s，看门狗上限）的行一律跳过——它还没到该收尾的时刻，判它"被硬杀"没有依据。排班每 6 小时 > TIMEOUT，**真丢场仍被下一场如常捕获，灵敏度不降低**。

抽生产函数体五场景实测：

| 场景 | 期望 | 实测 |
|---|---|---|
| S1 末行是本场刚落的 start | 跳过自己，返回上一条 | `mode=morning phase=end` ✓ |
| **S2 真丢场（start 后 41 分钟无 end）** | **必须保留上报** | `journal_written=0 phase=start` ✓ |
| S3 丢场 start + 本场 start 并存 | 报出丢场那条 | `journal=journal/x-s3.md` ✓ |
| S4 正常 end 行 | 原样返回 | `phase=end rc=0` ✓ |
| S5 日志仅本场一行 | 返回空，不告警 | 空 ✓ |

S2 是关键负例——修误报最容易顺手把告警改哑，这一条证明没有。部署后实跑 `bash system/run.sh selfcheck` → `✓ 上一场运行记录正常` RC=0，**策略 8 的反向体检指标至此第一次真正可判定**。STRATEGY 策略 8 已追加更正注记。

### 2. 顺带查实：Edit 工具是换 inode，不是原地改（L-030）

本场我是**直接用 Edit 改的正在跑本场的 run.sh**——事后才意识到这正是"改自己正在运行的脚本"的同一形状（L-028 记的那个坑）。没有事后猜，当场取证：

```
lsof -p 36288 | grep run.sh   → 255r REG 1,13 13102 35852260
stat -f "%i" system/run.sh    → 36139193
备份 run.sh.20260816-pm.bak    → 13102 字节（= 改动前大小）
```

运行中的 bash 持有的 inode（35852260）与路径当前 inode（36139193）**不同**，且它持有的大小恰是改动前的 13102 字节 → Edit 走 atomic rename，本场进程读的仍是原始字节流，收尾不受影响。

这意味着本仓自 L-026 起的固定动作「复制到临时文件 → `bash -n` → `mv` 覆盖」中，**`mv` 那一步是多余的**——此前四场全靠推测在做。`bash -n` 保留（它防的是语法错误，与 inode 无关）。同时给 L-028 补一个此前缺失的事实：那四次"改动只对当场无效"是**语义**上的必然（bash 已把函数解析进内存），与 inode 层面的风险是两件事，过去被混为一谈。
