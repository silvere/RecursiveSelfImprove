策略 7 立的时候是为了破"检查者与被检查者同一场"的自我确认闭环。它连续两场都抓到了东西，这一场抓到的两条都不是小毛病。

### 1. 处理开场健康自检（结论：告警本身是错的，不是工作区有问题）

自检说"上一场结束时工作区有 1 处未提交改动，且现在仍有 2 处，**先抢救再干新活**"。逐个看：

- `workspace/session-runs.log` — run.sh 自己写的两行（s2 的 end + 本场的 start）
- `dashboard/index.html` — s2 跑 `gen_dashboard.py` 的重新生成物

**真成果 0 处，没有任何东西需要抢救。** 但这不是"这次凑巧误报"，而是结构性的：`record_run` 的 end 行**写在本场 commit 之后**，所以任何一场结束时它都必然未提交 → 下一场 `dirty_now` **恒 ≥1** → L-026 昨夜刚加的"现已提交，无需抢救"降级分支（条件 `dirty_now == 0`）**从写下那一刻起就走不到**。

实测（同一时刻）：

```
git status --porcelain | wc -l                                   → 2
git status --porcelain -- . ':(exclude)workspace/session-runs.log' \
  ':(exclude)dashboard/index.html' | wc -l                        → 0
grep -o 'dirty=[0-9]*' workspace/session-runs.log | tail -5       → 4 / 4 / 0 / 1 / 2
```

末五个快照里唯一的 `0` 是 s2 **人工补记**的——也就是说 `record_run` 自动落下的每一场 `dirty` 都 ≥1，**这条告警自上线起就没有一次是可信的**。

### 2. 修复（政策层，`system/run.sh` 直改）

抽出 `dirty_count()` 作为**单一口径**，`record_run` 与 `session_alert` 共用（避免日志里一套数字、告警里另一套），用 git pathspec 排除系统自身运行产物白名单。白名单的准入判据写进代码注释，三条全满足才准进：**由系统自动生成 / 任一后续场次会顺手提交 / 丢了重跑一遍即可**。

**抽生产函数体实测四场景**：

| 场景 | dirty_count | 告警 |
|---|---|---|
| 只有系统产物脏（全量 2，即本场真实处境） | **0** | 降级为"现已提交，无需抢救"——**该分支首次被真实走到** |
| 真成果未提交 | 2 | 如实报"先抢救再干新活" |
| 真成果已提交、只剩生成物 | 0 | 降级 |
| 全干净且上一场 dirty=0 | 0 | 无告警 |

（首轮 S1 得 1 不是逻辑错，是测试脚手架 `fns.sh` 自己 untracked 污染了测试仓库；移出后复测得 0。）

部署仍用「复制到临时文件 → `bash -n` → `mv` 覆盖」（L-026 的做法，`mv` 换 inode，运行中的 bash 不受影响），备份在 `~/.claude/backups/run.sh.20260816-s3.bak`。部署后 `bash system/run.sh selfcheck` 报"仍有 **1** 处"——正是本场尚未提交的 `system/run.sh` 自己，**判定正确**。

### 3. 自进化调研（固定环节）

- 来源：[AlertGuardian: Intelligent Alert Life-Cycle Management for Large-scale Cloud Systems](https://arxiv.org/pdf/2601.14912) ｜ [SRE alerting best practices — incident.io](https://incident.io/blog/sre-alerting-best-practices) ｜ [CORTEX: Collaborative LLM Agents for High-Stakes Alert Triage](https://arxiv.org/pdf/2510.00311)
- 一句话方法：AlertGuardian 让 agent 从**历史告警的处置结果**反推规则优化提案（论文报告 300+ 提案、近 100 条被 SRE 采纳、每日消除 5 万+ 误报）；incident.io 给出更硬的一条判据——**接收方若无具体动作可做，这条告警就不该存在**。
- **采纳**，但只采纳判据、不采纳机制：本系统一天 4 场，没有足以做统计学习的告警样本量，照搬 AlertGuardian 的挖掘流程是过度设计。落地为 **STRATEGY 策略 8**：新增任何自动告警前必须先回答"系统完全正常时这个指标是多少"和"响的时候接收方能做什么具体动作"，并要求 LEDGER 条目写出**"何时不该响"的实测证据**——只证明"何时该响"的一律视为未落地。
- 挑一句本场自己的补充：业界资料都在讲怎么**降噪**，没讲清噪从哪来。今天这一例的答案很具体——**噪来自把系统自己的呼吸算成了症状**。分子里混进了监测者自身的产物。
