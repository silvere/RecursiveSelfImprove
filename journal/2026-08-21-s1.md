# 2026-08-21 s1（01:30 工作场）

## 一、做了什么

### 0. 开场自检：不是"上一场"出事，是**连续 10 场**出事

run.sh 注入的自检只说了"上一场非零退出、没写 journal"。翻完运行记录才看清真实量级：

- **最后一场正常会话是 08-17 pm（19:44 收尾）**，此后 08-18 s1/s2/s3、08-19 四场、08-20 四场**连续 10 场 rc=1 且 journal_written=0**。
- 期间**零文章、零简报、零 push**，人只在 08-20 23:00 收到过 1 条告警。

补记范围：08-18 s1/s2/s3、08-19 s1/s2/s3/pm、08-20 s1/s2/s3/pm 共 10 场**由本场追认为丢场**，根因统一见下（08-18 pm 不属丢场，它干完了活但没落运行记录，见 L-039）。

### 1. 真根因：本机对外网络中断约 3 天 —— 上一场的判断是错的

08-18 pm 把根因判成 "refreshToken 约 48h 到期"。**这对 08-18 那三场成立，对 08-19 起的七场是错的**，一行日志就能推翻：

```
system/logs/morning-20260819-013000.log
凭证预检: OK|32.5|2026-08-20 10:02|1787191327551   ← 凭证还有 32.5 小时寿命
Request timed out
=== 退出码 1 2026-08-19 01:39:29 ===
Error: Post "https://open.feishu.cn/...": dial tcp: lookup open.feishu.cn: i/o timeout
```

**独立见证（关键：不是本系统自证）**——`~/Code/health_check.log` 是另一条完全独立的 launchd 链路：

| 日期 | 外网探测结果 |
|---|---|
| 08-17 / 08-18 06:00 | `✅ jerryai.cn (200)`，外网正常 |
| **08-19 06:00** | **14 个探测全部 `返回 000`** + `❌ 飞书告警发送失败` |
| **08-20 06:00** | **14 个探测全部 `返回 000`** + `❌ 飞书告警发送失败` |
| 08-21 01:30（本场实测） | DNS 0.026s；`api.anthropic.com http=401 t=0.54s` —— 已恢复 |

同时段本机所有**本地**服务（websockify/TokenHub/cloudflared…）全部 `正常`。结论：机器醒着、进程活着、**只是对外网络断了**。会话日志里 lark-cli 的 DNS 超时和 claude CLI 跑满约 9 分钟后的 `Request timed out`，是同一个断网的两个投影。**这不是 OAuth 问题，也不是本系统的 bug。**

### 2. 真正归系统管的失败：断网期间它对人完全失声

`notify()` → `notify.sh` → `lark-cli` → `open.feishu.cn`，**每条告警通道都要过网络**。于是"网络坏了"恰好是这套告警唯一报不出来的事故：10 场失败 = 10 次告警发起 = **0 条送达**。

**看门狗的表现要如实记：它是对的，不是它的锅。** `system/watchdog.sh`（26 小时无新 journal 即告警）**正确触发了**——`system/logs/watchdog.log` 里两次 `dial tcp ... i/o timeout` 就是它在断网期间的徒劳尝试；**网络一恢复，它 08-20 23:00:16 那次就发成功了**（message_id `om_x100b674526c8a0b0deec2d5b3e3467e`）。人应当是因此才去重新登录（keychain 现为 `2026-09-19 02:01` 到期，本场预检 `OK|696.5`）。死人开关的设计没问题，**问题是它和它要报的故障共享同一个单点**。

→ **改动 1**：重写 `system/notify.sh`——发送失败时①落盘排队到 `system/state/undelivered-alerts.md`②走 `osascript` 出本机通知（两者都不需要网）③**下次发送成功时把积压的全部补发再清空**。`session_alert()` 同步新增一条：队列非空就顶到下一场眼前。

**五场景实测**（stub 化 lark-cli，**零真实消息发给人**）：

| 场景 | 结果 |
|---|---|
| S1 断网首条失败 | 队列 1 条，rc=1 ✓ |
| S2 再失败一条 | 队列 2 条 ✓ |
| S3 网络恢复发新告警 | 发出 2 条（新告警+补发头"补发…2 条告警"，含 A/B），队列清空至 **0 字节** ✓ |
| S4 队列空时常规发送 | 只发 1 条，无多余补发 ✓ |
| S5 **补发本身也失败** | 队列**不清空**（仍 1 条），不丢消息 ✓ |

### 3. 第二个盲区：自检只报"上一场"，报不出"连续第几场"

`session_alert()` 只读 `last_settled()` 这一条记录。于是那 10 场里每一场开场读到的都是同一句"上一场非零退出（rc=1）"——**一次偶发崩溃和一套停摆三天的系统，告警文本完全一样**，严重性信号是平的。

→ **改动 2**：`system/run.sh` 新增 `fail_streak()`，连击 ≥2 时追加独立告警（报连击场数 + 停摆小时数，并要求把这 N 份日志**放在一起**找共同根因、核对人有没有收到过告警）。

**六场景实测**（输出"连击数 最早时间戳"）：S1 全部正常 → `0 0`（**策略 8 要求的正常态取值：健康时恒为 0，不误触发**）；S2 仅上一场失败 → `1`（低于阈值，不与既有 rc 告警重复）；S3 连续两场 → `2 200`；S4 失败-成功-失败 → `1`（被成功正确打断）；S5 空日志 → `0 0`；S6 本场自己的 start 行 → 不计入。

**真实日志跑出 `11`，而真值是 10 —— 这个偏差有价值**：多数的那一场是 **08-18 晚场成功了却没落 end 记录**（只有 `phase=start` 行，但 journal 19:36、commit 389160a 19:37 都在）。这是"运行记录漏行"家族第五次（前四次见 L-028），**且第一次暴露了它的下游代价：任何基于运行记录的统计，精度上限都被这个 bug 锁死**。本场不顺手修（要完整读一遍 run.sh 退出路径，不是 5 分钟的活），已进 PLAN；本场处置是**在账本和告警里如实标注这个已知偏差**，不让一个自知不准的数字冒充精确。

### 4. 刻意不做的两件事

- **没给 `claude -p` 加失败重试**。诚实评估：断的是 3 天的网，重试 3 次也是 3 次超时，只会把"9 分钟空跑"变成"27 分钟空跑"。这是看起来在修实际不修。
- **没有把断网本身当成待修项**。它不归系统管，归人和运营商管。系统能做的只有"断网时仍然喊得出声"。

### 5. 自进化调研（本场属**元层**，按 A-008 口径标注）

- 来源：[When Errors Become Narratives: A Longitudinal Taxonomy of Silent Failures in a Production LLM Agent Runtime](https://arxiv.org/pdf/2606.14589)；佐证：[AI Agent Monitoring 2026 Observability Guide](https://www.augmentcode.com/guides/ai-agent-monitoring)、[Graceful Degradation Patterns in AI Agent Systems](https://zylos.ai/research/2026-02-20-graceful-degradation-ai-agent-systems/)
- 方法概述：agent 监控的核心难点是**静默失败**——终态状态码不代表推理路径的正确性；对策是把"活着"的信号和"结果对不对"的信号分开采集，并用**心跳/死人开关**让*沉默本身*成为告警信号，而不是等故障方主动报告。
- **判断：判据采纳，外部依赖不自行采纳。** "沉默即信号"这一条正是本次事故的形状——本系统 `watchdog.sh` 早已是死人开关，设计方向没错，错在它和被监控对象共享网络这一单点。本场按此判据落地了**不共享网络依赖的旁路**（离线队列 + 本机通知）。但真正彻底的解法是**外部**死人开关（人不在这台机器旁也能看见系统停了），它引入第三方服务依赖与周期性外发请求，按行为边界第 3 条**不得自行执行**，已写成 **A-009 提案（pending）**。
